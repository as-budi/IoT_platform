An ECA rule normally runs on the platform: devices send data, the platform decides, and the platform tells the actuators what to do. If the internet connection or the platform is down, the rule stops. Running rules on devices prepares a rule so that the devices involved can run it themselves, talking to each other directly by radio.

This is a preview. The platform already shows how a rule would be split, but devices do not run the plan yet. Firmware support comes in a later update.

Turning it on

  1. Open the ECA rule and click Edit.
  2. Switch on Also run on my devices and save.
  3. On the rule page, open Run on devices. It shows whether the rule can run on the devices, what each device would do, and anything that stops it.

The plan is saved each time you save the rule. If a device is replaced (new board, new MAC address), the page says the saved plan is out of date; click Update saved plan.

How a rule is split

  • Sensors broadcast the values the rule needs over ESP-NOW, a direct radio link between ESP32 boards. Only devices that take part in the rule use the values; the others ignore them.
  • The actuator (the device whose output the rule controls) checks the conditions itself, with the same timing as on the platform: for at least, cooldown, the clear condition, and ignore values older than.
  • Alarms, emails and Telegram messages stay on the platform and are sent when it is reachable.

Devices find each other by MAC address, so every device in the rule must have reported its MAC address (see Firmware updates and MAC address). They must also be on the same Wi-Fi channel, which is the case when they use the same access point.

What the result means

ResultMeaning
Runs on devicesEverything in the rule can run on the devices.
Partly on devicesControl actions run on the devices; alarms and messages stay on the platform.
Platform onlyThe rule cannot run on devices. The list under the result says why.

What can run on devices

  • ECA rules with the event New data for a variable in the conditions. Scheduled rules and "device sends no data" rules stay on the platform.
  • The rule needs at least one Set actuator or Send command action. A command needs a handler for its method in the device firmware.
  • At most {{ edge_limits.MAX_SIGNALS }} variables, {{ edge_limits.MAX_CONDITIONS }} conditions, {{ edge_limits.MAX_GROUPS }} OR groups, and {{ edge_limits.MAX_ACTIONS }} actions per device for each of "on activate" and "on clear".
  • A device can take part in at most {{ edge_limits.MAX_RULES_PER_DEVICE }} such rules and broadcast at most {{ edge_limits.MAX_PUBLISHED_SIGNALS }} variables.
  • Set Ignore values older than to a real limit (not 0), at most {{ edge_limits.MAX_AGE_LIMIT }} s. When a sensor stops sending, its value becomes unknown after that time, exactly as on the platform.
  • Devices compare 32-bit numbers. Prefer < and > over = with fractional thresholds.
  • The rule owner needs Operator access to the actuators, as for any rule that controls a device.

Two ways to split a rule

The page compares two arrangements. The rule uses the first one.

  • Actuator evaluates: each actuator checks the rule itself. A decision is made where the action happens, so no extra device has to work for the actions to run.
  • Sensor evaluates: one sensor checks the rule and broadcasts the decision to the actuators. All actuators follow one decision, but data from other sensors needs two radio hops, the actuators stop if that sensor stops, and the sensor must stay awake.

The comparison table shows how many devices must work, the longest radio path, and how many radio messages are sent while nothing changes.

Downloads

Download plan (JSON) gives the whole plan; JSON next to a device gives only that device's part; Download all (zip) gives every part in separate files. The files contain device MAC addresses and the rule logic, never access tokens.
