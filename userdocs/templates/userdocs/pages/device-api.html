Telemetry payload

All three protocols accept the same JSON:

FormExampleTime of the reading
Values only{"temperature": 25.1, "humidity": 60}when the platform receives it
Values with a time{"ts": 1791436800000, "values": {"temperature": 25.1}}ts in milliseconds since 1 January 1970 (UTC)
A list of either[{"ts": 1791436800000, "values": {...}}, {"ts": 1791436860000, "values": {...}}]per item, e.g. readings stored while Wi-Fi was down
  • Keys: letters, digits and underscores, starting with a letter, at most 50 characters. New keys become new variables.
  • Values: numbers; true/false are stored as 1/0. Text is rejected.
  • At most 1000 values per message. A time in seconds instead of milliseconds, or more than 5 minutes in the future, is rejected.
  • A message is saved completely or rejected completely, never partly.

HTTP

PurposeRequest
Send telemetryPOST {{ http.telemetry }}
Firmware report (version, board, MAC) and update progressPOST {{ http.firmware }}

Send the JSON as the body with the header Content-Type: application/json. Answers:

200saved; the answer lists new variables, e.g. {"saved": 2, "new_variables": ["humidity"]}
400the body is not valid JSON or breaks a rule above; {"error": "..."} explains why
401unknown access token
403the device is inactive
405use POST

Try it from a computer:

curl -X POST {{ http.telemetry }} -H "Content-Type: application/json" -d '{"temperature": 25.1}'

HTTP only carries data from the device. To receive requested states and commands, use MQTT or CoAP.

Use QoS 1 for telemetry, desired states, commands and responses. After switching an actuator, publish its new state as telemetry with the same key, e.g. {"lamp": 1}, so the platform can show In sync.

Online status with Last Will

Connect with a Last Will message offline (retained, QoS 1) on the status topic, then publish online (retained) there. The device then counts as online while the connection is open, and as offline as soon as the broker notices the connection is gone, instead of after {{ limits.offline_seconds }} seconds without data.

Trying MQTT from a computer

With the Mosquitto command-line tools (or a graphical client such as MQTTX):

mosquitto_pub -h {{ mqtt.host }} -p {{ mqtt.port }}{% if mqtt.tls %} --tls-use-os-certs{% endif %}{% if mqtt.login %} -u {{ token }} -P {{ token }}{% endif %} -t "{{ mqtt.telemetry }}" -m '{"temperature": 25.1}'
mosquitto_sub -h {{ mqtt.host }} -p {{ mqtt.port }}{% if mqtt.tls %} --tls-use-os-certs{% endif %}{% if mqtt.login %} -u {{ token }} -P {{ token }}{% endif %} -t "{{ mqtt.desired }}" -t "{{ mqtt.commands }}" -t "{{ mqtt.errors }}" -v

CoAP

Server coap://{{ coap.host }}:{{ coap.port }} (UDP, not encrypted). All resources start with api/v1/<token>:

MethodResourcePurpose
POST{{ coap.base }}/telemetrytelemetry, see payload; answer 2.04 Changed
GET (+ Observe){{ coap.base }}/desiredrequested states, e.g. {"pump": 1}; with Observe the server sends changes by itself
GET (+ Observe){{ coap.base }}/commandsopen commands: {"commands": [{"id", "method", "params"}]}
POST{{ coap.base }}/commands/<id>/response{"success": true, ...}
POST{{ coap.base }}/firmwarefirmware report and update progress

Error answers use CoAP codes: 4.00 wrong payload, 4.01 unknown token, 4.03 device inactive, 4.04 unknown resource. A device that uses Observe should send something at least every few minutes, so routers keep the UDP path open, and should observe again if notifications stop.

Try it with coap-client from the libcoap tools:

coap-client -m post -t json -e '{"temperature": 25.1}' {{ coap.base }}/telemetry
coap-client -m get -s 60 {{ coap.base }}/desired
